# Instalação na VM — 16/10/2026

## Ambiente e mudanças realizadas

O laboratório foi instalado em `/home/gabriel/lab-agentes-externos` na VM `192.168.122.131`, usuário `gabriel`, hostname `vm-lab-pesq`, Ubuntu 26.04.1 LTS, arquitetura x86_64. A conexão SSH por chave já funcionava; não foi necessário alterar as chaves. Nenhuma senha de acesso foi gravada nos arquivos do projeto.

A VM possui 2 CPUs, aproximadamente 3,3 GiB de RAM visível e 2 GiB de swap. O disco virtual tem 25 GB. A raiz usava um LV de 11,5 GiB, com 11,5 GiB ainda livres no grupo `ubuntu-vg`. Após autorização explícita, o LV e o filesystem ext4 foram ampliados online para aproximadamente 23 GiB, sem modificar partições ou adicionar discos.

Pacotes instalados: `docker.io`, `make`, `ripgrep` e dependências resolvidas pelo Ubuntu; `curl` e suas bibliotecas foram atualizados pelo APT. Python, OpenSSL, certificados e jq já estavam presentes. `socat` foi instalado para o encaminhamento TCP da aplicação. Docker foi habilitado e `gabriel` incluído no grupo `docker`.

As CLIs ficam em `.state/bin`: kind 0.33.0, kubectl 1.34.0, Helm 3.19.0, Hubble 1.20.2 e containerlab 0.81.1. Os downloads foram conferidos por checksums oficiais. `make tools` instala as primeiras quatro; containerlab foi obtido separadamente do arquivo oficial `containerlab_0.81.1_linux_amd64.tar.gz` e validado contra `checksums.txt` da mesma release.

O código foi transferido sem `.state`, bancos, credenciais ou caches do host. O cluster anterior do host não foi recriado. A VM recebeu um cluster dedicado `agent-trap-lab`, aplicação, Cilium/Envoy, Hubble Relay/UI, Prometheus e Grafana.

## Topologia implantada

```text
VM 192.168.122.131
  Docker network kind
    agent-trap-lab-control-plane : 172.18.0.2
      Kubernetes
        trap, Prometheus, Grafana
        Cilium/Envoy, Hubble Relay/UI
    clab-agent-trap-clients-client : 172.18.0.3
    clab-agent-trap-clients-reference : 172.18.0.4

  Clientes -> 172.18.0.2:30080 -> HTTP L7 -> trap:8080
```

Os IPs Docker acima são os observados na instalação, não um contrato fixo. Consulte `make node-ip` e `docker inspect` após recriar a infraestrutura.

[infra/clients.clab.yaml](infra/clients.clab.yaml) define os dois clientes Linux. Eles usam a imagem local `agent-trap-lab:local`, permanecem ociosos com `sleep infinity` e recebem `tools/smoke.py` como bind mount somente leitura. A topologia reutiliza a rede Docker `kind` existente, sem criar um cluster adicional ou roteadores virtuais. O containerlab adicionou suas entradas de hosts e configuração SSH dos nodes na VM.

O cliente `client` usa `LabContainerlabClient/1.0`; `reference` usa `GPTBot/1.0` sintético. Este segundo cliente não representa uma conexão real da OpenAI e não autentica origem. Ambos são scripts determinísticos, sem LLM.

| Interface | URL |
|---|---|
| Aplicação e variantes | http://192.168.122.131:18080/ |
| Dashboard Grafana | http://192.168.122.131:13000/d/agent-trap-lab |
| Alvos Prometheus | http://192.168.122.131:19090/targets |
| Hubble UI | http://192.168.122.131:18081/ |

O acesso direto e persistente no IP privado foi autorizado explicitamente. As interfaces de consulta permitem acesso sem login a quem alcançar esse IP. Grafana usa acesso anônimo Viewer; administração usa a senha aleatória em `.state/grafana-admin-password`. Nenhuma abertura de acesso público ou alteração no roteador do host foi realizada. O endereço libvirt/NAT é alcançável pelo host; não implica acesso automático de outras máquinas.

Os acessos usam quatro unidades systemd, executadas como `gabriel`, com reinício automático em caso de saída:

| Serviço | Funcionamento |
|---|---|
| `agent-trap-http` | socat: IP privado:18080 -> loopback:18080 -> NodePort kind |
| `agent-trap-grafana` | kubectl port-forward para Grafana, 13000 |
| `agent-trap-prometheus` | kubectl port-forward para Prometheus, 19090 |
| `agent-trap-hubble-ui` | kubectl port-forward para Hubble UI, 18081 |

O proxy TCP da aplicação preserva o caminho pelo NodePort, mas pode modificar o peer observado; não use esse acesso para concluir o IP original. Os clientes containerlab acessam diretamente o node Docker e foram o caminho utilizado na validação L7.

[scripts/vm-access.sh](scripts/vm-access.sh) instala/controla as unidades em `/etc/systemd/system`. Elas independem da sessão SSH. O teste não incluiu reinicialização da VM: serviços de acesso habilitados não garantem sozinhos a retomada de todo o laboratório. O node kind possui política Docker `on-failure`; após reiniciar a VM, confira os containers antes de usar `make up`. Não tente adotar/substituir um cluster antigo sem verificar seu estado.

## Operação na VM

Entre por SSH:

```bash
ssh gabriel@192.168.122.131
cd /home/gabriel/lab-agentes-externos
export PATH="$PWD/.state/bin:$PATH"
```

Confira os componentes:

```bash
kubectl --kubeconfig .state/kubeconfig get nodes
kubectl --kubeconfig .state/kubeconfig -n agent-trap-lab get pods,pvc
kubectl --kubeconfig .state/kubeconfig -n kube-system get pods
docker ps
sudo ./scripts/vm-access.sh status
```

Execute novas rodadas sintéticas:

```bash
make topology-test
python3 tools/check_observability.py
```

Não é necessário executar `make grafana` ou `make prometheus` enquanto os serviços systemd ocuparem essas portas. Esses comandos são alternativas temporárias aos serviços, não complementos.

Capture fluxos quando necessário:

```bash
make observe
```

A captura permanece vinculada a esse comando e grava `.state/hubble.jsonl`; Ctrl-C encerra o processo. Não foi instalado um coletor permanente de fluxos. Métricas Prometheus continuam sendo coletadas independentemente da CLI.

## Parar para liberar recursos

Dentro da VM, na pasta do laboratório:

```bash
sudo ./scripts/vm-access.sh stop
make topology-down
./scripts/destroy.sh --confirm
```

A ordem encerra os serviços de acesso, remove os clientes containerlab preservando a rede compartilhada e remove o cluster kind. Dados em `.state/node-data` e ferramentas locais permanecem. `make destroy` sozinho remove somente o cluster, não os clientes containerlab nem as unidades de acesso.

Para recriar após essa remoção:

```bash
make up
make topology-up
sudo ./scripts/vm-access.sh start
```

O comando `topology-up` pressupõe cluster/imagem existentes e não usa `--reconfigure` para substituir topologias silenciosamente. Se os clientes já existem, use `topology-test`; para recriar, remova primeiro com `topology-down`.

Se o IP privado mudar, atualize a exposição explicitamente:

```bash
sudo ./scripts/vm-access.sh install NOVO_IP_PRIVADO
```

## Evidências de validação nesta VM

- Dez testes da aplicação passaram com Python 3.14.3 do Ubuntu; a imagem da aplicação continua usando Python 3.12.
- Deployments da aplicação, Prometheus e Grafana ficaram Ready; os três PVCs ficaram Bound.
- Os dois clientes containerlab ficaram ativos e seus smokes retornaram PASS.
- Após a conclusão das gravações, o resumo registrou 22 eventos, oito exposições e seis desafios com primeiro retorno válido. Os dois controles permaneceram sem retorno válido.
- Captura Hubble com 88 eventos HTTP L7 confirmou os headers `LabContainerlabClient/1.0` e `GPTBot/1.0`.
- Os alvos `trap`, `cilium-agent` e `prometheus` ficaram saudáveis. As 17 consultas dos 16 painéis foram executadas por API; a verificação final retornou séries em todos os painéis.
- Aplicação, saúde Grafana, readiness Prometheus e página Hubble UI responderam HTTP 200 pelo IP privado, a partir do host.
- As quatro unidades de acesso ficaram `active` após encerrar a conexão de instalação.
- No snapshot final, a VM usava aproximadamente 1,6 GiB de RAM, tinha 1,7 GiB disponíveis, cerca de 147 MiB de swap utilizados e 11 GB livres na raiz. Esses números variam com a execução.

O servidor grava eventos após produzir a resposta HTTP. Por isso um resumo consultado imediatamente pelo smoke pode mostrar 10/21 eventos, enquanto o estado final estabiliza em 11/22. A contagem de retornos únicos deriva diretamente do estado dos desafios.

Foi corrigida uma corrida de inicialização em `scripts/up.sh`: o Helm podia retornar antes do registro da CRD `CiliumNetworkPolicy`. O provisionamento agora espera o rollout do daemonset Cilium e a condição Established da CRD antes de aplicar os workloads.

Esta validação não mediu detecção de IA, não usou modelos reais, não avaliou HTTPS e não verificou renderização visual dos painéis em navegador. As evidências completas da implementação original permanecem em [VALIDACAO.md](VALIDACAO.md).
